# Tasmota CC1101 网关开发经验与踩坑记录

> 本文件总结 `tasmota32solo1`（ESP32-SOLO1 单核）+ CC1101 433MHz 网关项目开发中遇到的问题与解决方案，供后续开发少走弯路。
>
> 适用技术栈：Tasmota 15.5.0 (solo1) + Berry 脚本（WebUI/业务）+ C 驱动（`xdrv_74_cc1101.ino`）+ PlatformIO。

---

## 1. Berry 应用层踩坑

### 1.1 Berry 的 `path` 模块没有文件读写函数

**错误用法（Python 风格，Berry 不存在）：**

```berry
var content = path.read_file("/rf_remotes.json")   # 报错: attribute_error
path.write_file("/rf_remotes.json", content)        # 报错: attribute_error
path.rename(a, b)                                    # 报错: attribute_error
```

**原因：** Berry 的 `path` 模块只有路径操作函数：`isdir / isfile / exists / split / splitext / join`，**没有** `read_file / write_file / rename`。

**正确用法（Berry 内置 `open()` 文件 API）：**

```berry
# 读文件
if path.exists(filename)
  var f = open(filename, "r")
  var content = f.read()      # 读取全部剩余内容，返回 string
  f.close()
end

# 写文件（覆盖）
var f = open(filename, "w")
f.write(content)
f.close()

# 文件对象方法：read / readbytes / readline / write / seek / tell / size / flush / close
```

> 文件不存在时 `open(..., "r")` 会抛 `io_error`，读文件前先用 `path.exists` 判断或包 `try/except`。

### 1.2 webserver：HTML 页面与 JSON API 响应要区分

**HTML 页面（含样式、按钮）：**

```berry
webserver.content_start("Page Title")   # 发送 HTML 响应头 + 标题
webserver.content_send_style()          # 可选：发送 Tasmota 样式
webserver.content_send("<p>content</p>")
webserver.content_stop()                # 必须成对，结束响应
```

**JSON API（前端轮询的纯数据接口）：必须用 `content_response`**

```berry
webserver.content_response(json.dump({"value": 123}))  # WSReturnSimpleString，正确设置响应头并结束
webserver.content_response("")                          # 返回空也要用 content_response
```

**坑：** 用 `content_send` 返回 JSON 且不 `content_stop` 时，HTTP 响应会异常结束（客户端报 `ResponseEnded`），前端 `XMLHttpRequest` 的 `x.status`/`x.responseText` 判断失败 → 页面永远等不到数据（表现为"录制页面一直 Listening 无反应"）。

### 1.3 `except` 必须带变量（Tasmota 扩展语法）

```berry
try
  ...
except .. as e, m          # e=错误类型, m=错误消息；必须带
  log(f"CC1: error {e} {m}", 3)
end
```

无变量 `except` 可能引起语法解析错乱，报错位置往往在文件后面某处（误导排查）。

### 1.4 Berry 严格模式：except 块内禁止裸 `nil`（无副作用表达式）

```berry
except .. as e, m
  nil       # ❌ 报错: strict: expression without side effect detected
end
```

**后果严重：** 一旦脚本有语法错误，整个 `.be` 文件加载失败（串口日志 `BRY: failed to load`），依赖该脚本注册的 **WebUI 路由/按钮全部消失**（例如 433 Gateway 主菜单按钮没了），且编译期不报错（Berry 是运行时加载）。

**正确做法：** except 块内至少放一条有副作用的语句（`log(...)` 或 `return`）。

### 1.5 Berry 脚本错误不在编译期暴露

- `pio run` 编译通过 ≠ Berry 脚本正确。Berry 在设备启动时（`autoexec.be` → 驱动脚本）才编译加载。
- **每次改完 `.be` 文件并烧录后，必须重启看串口启动日志**：
  ```
  BRY: Berry initialized, RAM used 3075 bytes
  BRY: failed to load '/cc1101_gateway.be' (syntax_error - ...)   # ← 有问题
  BRY: Successfully loaded 'autoexec.be'                           # ← 正常
  ```

### 1.6 C 函数返回值给 Berry：`be_return` 只返回栈顶 1 个值

```c
// ❌ 期望 var a,b,c = f() 拿到 3 个值，实际全为 nil
int be_xxx(struct bvm *vm) { be_pushint(vm, 1); be_pushint(vm, 2); be_return(vm); }

// ✅ 正确：返回 JSON 字符串，Berry 端 json.load 解析
int be_xxx(struct bvm *vm) {
  be_pushstring(vm, "{\"Value\":1,\"Bits\":24}");
  be_return(vm);
}
```

```berry
var rx = json.load(cc1101_receive())
var value = rx.find("Value", 0)
```

### 1.7 Berry 调试技巧

- 用 `log(f"...", 3)` 打印日志，串口可见（过滤关键字 `BRY` / `CC1` / `Exception`）。
- web handler / every_50ms 等入口务必包 `try/except .. as e, m` 并 `log`，否则异常静默。
- `tasmota.rtc()["local"]` 在时间未同步时可能为 nil，取值前做保护。

## 2. CC1101 硬件调试经验

### 2.1 分层排查法（重要）

433 遥控接收链路分 3 层，逐层确认：

```
① 信号到达硬件?   → 读 RSSI 状态寄存器（CC1101_RSSI=0x34）
② 解调数据流输出? → GDO0 引脚是否有电平跳变
③ 解码协议?       → RCSwitch 是否解出 value/protocol
```

- **RSSI 计算：** `rssi = (raw / 2) - 74`（raw 为状态寄存器值，注意有符号处理）。`RSSI > -50 dBm` 视为有信号活动。
- **GDO0 检测注意采样率：** 50ms 轮询会错过 2kbaud 信号（约 500µs/bit）。要用 1ms 内多次采样统计跳变，才能可靠判断 GDO0 是否输出数据流。

### 2.2 解码失败的最关键配置：`MDMCFG2`

| 值 | 含义 | 结果 |
|----|------|------|
| `0x02` | ASK/OOK，Manchester 关闭 | ❌ GDO0 无有效数据流，RCSwitch 不解码 |
| `0x32` | ASK/OOK + **Manchester 使能** | ✅ 照搬旧项目实测配置，解码成功（24位/协议1） |

> **根因教训：** 一开始猜测"需要同步串行模式 / data whitening"等方向都失败，最后照搬旧项目实测可解码的寄存器组合一次性解决。**遇到芯片调试问题，先找一份"同一芯片+同一用例"的已知可工作配置对照，不要从零猜寄存器。**

### 2.3 433.92MHz ASK/OOK 接收完整配置（已验证）

```
IOCFG2    = 0x0D   # GDO2 同步数据输出
IOCFG0    = 0x0D   # GDO0 数据输出（RCSwitch CHANGE 中断）
PKTCTRL1  = 0x06
PKTCTRL0  = 0x32   # 可变长度包，无 CRC
MDMCFG4   = 0x06   # 数据率 ~2kbaud
MDMCFG3   = 0x43
MDMCFG2   = 0x32   # ★ ASK/OOK + Manchester 使能（解码关键）
DEVIATN   = 0x47
FREQ2/1/0 = 0x10 0xB0 0x71   # 433.92 MHz
FREND0    = 0x11
MCSM0     = 0x18
FSCAL3/2/1/0 = 0xE9 0x2A 0x00 0x1F
TEST2/1/0 = 0x88 0x31 0x09
PATABLE   = 0x60
最后 strobe SRX 进入接收
```

### 2.4 Normal/FIFO 模式下 GDO0 不输出解调数据

- `PKTCTRL0=0x00`（Normal/FIFO）下，即使 `IOCFG0=0x0E`，GDO0 也不输出解调数据流（被包状态机占用）→ RCSwitch 无法工作。
- 之前测试过同步串行模式 `0x40/0x45` 等，未成功进入可解码状态；最终确认 `0x32` 组合（配 `MDMCFG2=0x32`）有效。

### 2.5 参考旧项目要核实数据链路

旧项目（SmartRF-IDF）文档记录"RCSwitch 解码成功"，但其实际硬件链路是 **RCSwitch 从独立 GPIO13 读信号（独立接收器）**，不是从 CC1101 的 GDO0 取数；且 ESP8266/ESP32 接线不同。**照搬配置前必须核实"信号源→解码"的完整链路是否一致。**

## 3. 构建与烧录环境

### 3.0 可复现编译（配置已入库）

本项目的关键编译配置已经强制提交到仓库，新电脑 clone 后不需要手工复制：

- `platformio_override.ini`：定义本项目专用的 `tasmota32solo1` 环境，并已设为默认环境。
- `platformio_tasmota_cenv.ini`：被 `platformio.ini` 的 `extra_configs` 加载。
- `tasmota/user_config_override.h`：CC1101、Berry、RCSwitch、文件系统等编译开关。

安装 PlatformIO 后直接编译：

```powershell
python -m platformio run -e tasmota32solo1
```

产物位于 `.pio/build/tasmota32solo1/firmware.bin` 和 `firmware.factory.bin`。

### 3.1 沙箱限制与 `.pio_home`

- 默认 PlatformIO home `C:\Users\wedo\.platformio` 的 `platforms.lock` 会被沙箱阻止写入。
- 解决办法：把 home 指到项目内目录，同时用**系统完整 Python** 运行 PlatformIO：

```powershell
$env:PLATFORMIO_HOME_DIR = "d:\VC\Tasmota\.pio_home"
& "C:\Users\wedo\.platformio\penv\Scripts\python.exe" -m platformio run -e tasmota32solo1 -t upload --upload-port COM3
```

### 3.2 `.pio_home` 精简 Python 缺 `_socket` 的修复

**现象：** littlefs 导入失败：
```
ModuleNotFoundError: No module named '_socket'
ImportError: cannot import name 'lfs' from partially initialized module 'littlefs'
```

**原因：** `PLATFORMIO_HOME_DIR=.pio_home` 后，PlatformIO 用 uv 在 `.pio_home\penv` 创建的精简虚拟环境**缺少标准库 C 扩展**（如 `_socket.pyd`）。

**修复：** 把完整的系统 penv 镜像到 `.pio_home`：

```powershell
robocopy "C:\Users\wedo\.platformio\penv" "d:\VC\Tasmota\.pio_home\penv" /MIR /NFL /NDL /NJH /NJS /R:1 /W:1
```

验证：`& "d:\VC\Tasmota\.pio_home\penv\Scripts\python.exe" -c "import socket; print('OK')"`

### 3.3 烧录分区与 LittleFS

- `pio run -t upload` 会烧录 firmware.bin + littlefs.bin（0x3b0000，约 327680 字节，含 Berry 脚本）。
- **改 `.be` 脚本后必须重新 `pio run -t upload`**（重新打包 littlefs.bin），固件 `.bin` 不变。
- 每次完整编译烧录约 6-7 分钟，调试时尽量批量修改再烧录。

### 3.4 临时文件管理

- `.gitignore` 已加入 `.pio_home`，避免构建环境被提交。
- 调试脚本（如串口监听 .ps1）、编译产物（`a.out`）不要提交，用完删除。

## 4. 调试方法论总结

1. **分层定位**：先确认"哪一层断了"（信号→数据流→解码），再深入，避免在错误层反复试错。
2. **硬件对照**：芯片寄存器配置优先参考"同芯片+同用例"的已知可工作配置。
3. **脚本变更必查启动日志**：Berry 脚本语法错误不在编译期暴露，烧录后必须重启看 `BRY: failed to load`。
4. **API 先查存在性**：使用 Berry 模块方法前，先确认方法存在（`path` 模块、`webserver` 模块等），避免照搬其他语言习惯。
5. **每次改动一个变量**：寄存器/配置逐项验证，保留能工作的配置版本记录。
